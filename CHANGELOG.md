# Change Log
All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](http://keepachangelog.com/).

## [4.0.0] - Unreleased

### Added 

#### Odatix

- Add `odatix dse`: search a design space instead of sweeping it. Odatix has always run every configuration an architecture describes, which is the right thing to do with forty of them and the wrong thing with forty thousand — what four or five parameters already amount to. An exploration runs the same synthesis, on the same architectures, with the same parameters; it evaluates a batch, looks at what came out, and chooses the next batch from there. Nothing about the architectures changes: a search reads the very same parameter space a sweep enumerates
- What an exploration has to be told, and a sweep does not, is a **campaign**: a file of the new `odatix_userconfig/dse_campaigns/` directory saying what evaluating a design runs (`run`, `tool`, `flow`, `target`), what makes a design good (`objectives`), how long to look for it (`search`) and which architectures to search. Everything else — the frequency bounds, the timeouts — keeps coming from the settings file of the command being run, whose selection an exploration fills in without ever writing over the one the user keeps
- How an exploration is *run* is a different question from what it looks for, and lives in `odatix_userconfig/dse_settings.yml`: the usual run settings (`nb_jobs`, `overwrite`, `ask_continue`, ...) and `campaigns`, which names the campaign files to run, in order. That is what lets two campaigns search the same architecture with the same parameter domains: asking *how small can this get* and *how fast can this get* of one design are two files, so two names, so two answers side by side — a campaign is named after its file, and so is everything it writes (`results/dse/<campaign>.yml`, `results/results_dse_<campaign>.yml`). `-p/--campaign` runs one without touching the settings file, and `-a/--architecture` still restricts what the selected campaigns explore
- An objective is a metric to `min` or to `max`, and nothing says how the objectives compare to each other: a smaller design that runs slower is not worse than a bigger one that runs faster, it is another trade-off. So what a campaign returns is not one design but every design nothing beats on all objectives at once — the Pareto front. Any metric of the results file works, derived metrics included, as does any dimension a record carries as a number (`frequency`, where an fmax synthesis puts its answer). A design synthesized at several frequencies is worth what its best record is worth
- Objectives are what a design is good at; `constraints`, in the campaign file, are what it has to be for it to count at all — each one a metric with a `min`, a `max`, or both (`Slack` at least `0`, `LUT_count` at most `20000`). The two are different questions, and writing the first as the second is what a search does badly: `Slack, goal: max` spends the budget pushing the slack up long after it stopped being worth anything, and leaves designs that miss the timing on the front, since one that fails by a nanosecond is still the smallest anybody found. A design that breaks a constraint is not a trade-off, it is a design that does not work. Infeasible designs are ranked rather than dropped: a design that meets the constraints beats one that does not whatever the objectives say, and between two that both miss them the one closer to meeting them wins — at the start of a search there are often only infeasible designs, and they are what points it towards the part of the space that works. So the front holds feasible designs as soon as any were found, and while none were it holds the closest the search got, said outright after every batch and written to the archive (`feasible`, `unmet`) rather than left to be noticed. Getting closer to feasibility counts as progress for `patience`, so a batch that finally meets the constraints is not read as having achieved nothing

- An objective is not restricted to what a synthesis measures. `simulations`, in the campaign file, names simulations every design of a batch is run through as well — alongside its synthesis, in the same session, still counting as one design out of the budget, and simulated once whatever number of frequencies the search gave it. The simulated number reaches the search the way it reaches the charts, through a derived metric that copies it onto the synthesis result or computes something out of both (a cycle count becoming a runtime in microseconds), so a search that optimizes what a design *does* needs nothing new: the derived metrics of the workspace are recomputed after every batch, before anything is read, and what comes out is an ordinary metric of an ordinary record. Leaving `simulations` empty does not turn derived objectives off — a workspace whose designs were simulated beforehand gets them just the same, without running anything twice
- An exploration is not restricted to synthesis: `run: workflow` in a campaign file searches a **workflow** the same way, the names under `architectures` then being workflows and the metrics under `objectives` and `constraints` the ones its `_metrics.yml` reads out of what its commands wrote. A workflow is swept exactly like an architecture -- same parameter domains, same configurations, same generation rules -- so nothing about the search changes; what changes is that no eda tool runs anything (`tool`, `flow` and `target` say nothing, and the results are read from `results/results_workflow.yml`). This is often where an exploration is worth the most: a workflow's knobs are arguments on a command line, so five of them describe a hundred thousand runs without anything having to be built for it. The domains of a workflow are axes of the search even when they substitute nothing into a file, which is what a workflow reading them as `${domain}` in its commands looks like
- New example, `image_codec`: a small block-transform image codec, written with the standard library only, whose four knobs (quantization quality, transform block size, downsampling, dead zone) describe 3150 encoders and pull against each other -- every one buys quality with bitrate or bitrate with quality. The campaign `image_codec_rate_quality` searches sixty of them for the rate/quality curve none of them is beaten on, under a constraint on the encoding time, and needs no eda tool to run
- A workflow run now records what a synthesis run already recorded: the configuration of each of its parameter domains, and where the job sits in the design space of its workflow. So the results a sweep of a workflow produced are designs an exploration started later is given for free, the way `reuse_results` has always given it the synthesis results of the workspace

- An exploration running `custom_freq_synthesis` says at what frequency, in the `frequencies` section of its campaign file. It is the one run that is *told* a frequency -- an fmax synthesis looks for one -- so it is the one run where the frequency is a choice like any other: either it is fixed here (`list`), and every design is synthesized at each of those while the search moves along the parameters only, or it is left to the search (`explore: Yes`, within `range`), which then treats it as one more axis of the space and gives each design its own. Exploring it is what makes a custom frequency synthesis worth searching, the trade-off it is run for being the one between the frequency asked for and what the design costs at it. Saying nothing leaves the frequencies of `synth_settings.yml` alone, like every other setting of the command being run
- An exploration also searches **what runs a design**: `tool`, `flow` and `target` in the campaign file each take one name, fixing it for every design, or a list, which the search then chooses between. The three are one axis rather than three, since a flow is declared by a tool and a target is enabled by one: what the search moves along is the combinations the workspace can actually run, and a tool, a flow or a target it does not hold stops the exploration before anything is synthesized. Like the frequency, this is not a parameter of the architecture — the same rtl built by two tools or for two targets is the same rtl — but it is a trade-off all the same, and it is what an exploration asking *which target is this design cheapest on* is made of. A design run by two toolchains counts as two designs, each with its own place on the front, and its results are read back from the results file of its own tool. On the command line, `-t/--tool`, `-f/--flow` and the new `--target` are repeatable and mean the same thing
- Naming targets in an exploration does not rewrite `target_<tool>.yml`, which is where targets are turned on and off and is shared by every run: a run can now be told which of the enabled targets to work on (`Run(..., targets=[...])`), and an exploration searching the targets runs them one at a time without the file meaning different things at different moments. Saying nothing keeps what every run has always done — every target the file enables, a design being worth what its best target is worth
- Four search strategies. `exhaustive` walks the whole space in sweep order — it is what Odatix already did, said as a search, so a full sweep and an exploration are the same command with a different word in the settings. `random` samples uniformly, the baseline any search has to beat. `genetic` keeps the designs that turned out well and looks around them: a new design is made of the parameters of two already evaluated, with one parameter changed now and then, parents drawn towards the front and, within the front, towards the designs whose neighbours are far away — so the search spreads along the trade-off curve instead of piling into one end of it. Only the best `population` designs are kept to look around (four batches' worth by default): a parent is drawn out of a bounded population, so the odds of looking around a good design stay the same however long the search runs, where looking around everything ever evaluated would dilute them batch after batch until the search was sampling at random. `bayesian` fits a Gaussian process to each objective instead of only ranking what it has run, and proposes the design expected to grow the front's hypervolume the most, estimated by drawing samples from what each model believes about a candidate and averaging the hypervolume they would add — worth the extra thinking between two designs once a design costs an hour of synthesis. Like `genetic`, it opens with a handful of random designs, there being nothing yet to fit a surface to. Constraints are modeled separately, since a constraint is not an objective: one more Gaussian process learns how far a design is from meeting them, and the probability it gives of a candidate being feasible at all multiplies the expected gain — so a design the model expects to be excellent and infeasible is ranked for what its chances are worth, rather than proposed again and again. Until anything feasible has been found there is no front worth growing, and the search ranks candidates by how close to feasible the model puts them instead. The constraints share that one model by default, fit on their total; `constraint_models: true` gives each of them a model of its own, which is finer when two constraints are missed along two different axes, and costs one more model to fit per constraint on every refit
- Add `mode: async` (`-m/--mode`), for any strategy: `batch` mode, the only one there was, proposes a batch and waits for every design in it before deciding what to run next, which leaves every other slot idle when one design in the batch runs far slower than the rest — ordinary in EDA synthesis, where two designs a parameter apart can close timing five times slower than each other. `async` mode removes that wait: a new design is submitted the moment a slot frees, so a straggler ties up its own slot and nothing else. `batch` still says how many designs run at once, now meaning how deep that queue is kept rather than how many are decided together. Paired with `bayesian`, whose model is refit and asked again after every single design that comes back, this is what makes the strategy ask one question at a time instead of a whole batch's worth; a design still in flight is fed back into the model at its own predicted value in the meantime, so two proposals made moments apart do not land on top of each other
- A campaign stops on its `budget` (designs evaluated at most, per architecture), when the space runs out, or on `patience` (batches in a row that do not push the front any further out). A `seed` makes a search reproducible, which is what tells a change in the rules from noise when an evaluation costs an hour of synthesis. No design is ever evaluated twice
- What counts as a batch that got somewhere is how much further the front reaches — its hypervolume, written in the archive next to it — and not which designs are on it: asking whether the front changed says yes to a design a hair better on one objective just as readily as to one that opens up a whole region of trade-offs, so an exploration would either go on for hours over rounding or stop in the middle of getting somewhere. `improvement` is how much of the front a batch has to add to count (`0.02`: two percent)
- What is searched is what the architecture already declares: the variables of a parameter domain that describes its configurations with rules (resolved on the spot, without anything having been generated first), the configurations of a domain holding only files, and the variables of the architecture itself when they feed its commands — the virtual parameter domains, where a design generated by high-level synthesis has all of its knobs, and the case an exploration is most needed for. Variables sharing a `group` share an axis, chosen together exactly as a sweep pairs them
- Each campaign writes `results/dse/<campaign>.yml`: what it evaluated, in order, and which of those designs are the answer. It is rewritten after every batch rather than at the end, because an exploration is long and will be interrupted. The metrics themselves are exported as any run exports them, so Odatix Explorer reads them like any other result
- The designs a campaign evaluated are also exported as a results source of their own, `results/results_dse_<campaign>.yml`. It is an ordinary results file — the same records, the same metrics, read by Odatix Explorer like any other source — with the search written into every record: which campaign evaluated the design (`dse`), which batch proposed it (`dse_batch`), whether nothing dominates it (`dse_front`) and whether it meets the constraints (`dse_feasible`). Which is what makes *plot the area against the frequency, colored by whether it is on the front* an ordinary chart on any page of the explorer rather than a feature. The file is rewritten whole after every batch, so a design a later batch pushed off the front stops being marked as being on it; nothing in it is a new result, so deleting it loses the marking and not the results
- The archive now also holds `history`: what the front was worth after each batch, how many designs were on it and how much of the objective space it covered. The whole curve is measured again on every save, against the range of every objective as it is known then — a hypervolume measured against a corner that has moved since does not belong on the same curve as one that was not, and two batches have to be comparable for the curve to mean anything
- Add an **Exploration** page to Odatix Explorer, for what a results file cannot say: the search itself. It picks a campaign of the workspace and shows its trade-off curve drawn over the designs it beat — a front alone says what the answer is, a front over the cloud it came out of says what had to be given up for it — how the front grew batch after batch, the front design by design, and the designs that produced nothing and why (a campaign where half the designs failed to build has not searched the space it thinks it searched). It reads the archives directly and polls, an exploration being meant to be watched while it runs. When a campaign pulls in more directions than a chart has axes, the trade-off curve says which two it is drawing and lets them be chosen — plus a third, which turns it into a cloud in a volume; the metrics a constraint names are offered as axes too, *what did the answer cost in slack* being a trade-off worth seeing even though nothing was optimizing for it
- An exploration runs like every other Odatix command: it says what it is about to spend and asks once (`Continue? (Y/n)`) in the terminal it was typed in, nothing running before that answer or `-y`, and then lives in the daemon under the monitor. The search itself is a job of the session — the first one, kept at the top of the monitor whatever else is running: its log is what the search has to say, and its progress bar is how much of the exploration is behind. The designs it decides to evaluate appear underneath it, in the same session. So the monitor can be closed and attached again (`odatix monitor`) without stopping the search, and `-d/--detach` starts an exploration without opening it at all
- The log of that job is the story of the search and nothing else — what each batch changed, what it could not measure, where it stopped. The banner, the plan already shown in the terminal and what running a batch says about itself stay out of it; a run that refuses to start still explains itself, in the message saying the batch did not run
- The search takes none of the parallel job slots it fills: `odatix dse -j 8` runs eight synthesis jobs, not seven and a search
- An exploration picks up where an interrupted one left off: what it evaluated is read back from its archive, counts against the budget and is not proposed a second time. Killing the search from the monitor leaves the batch it had already enqueued running, and those results are read by the next run instead of being synthesized again. `-o/--overwrite` starts over instead
- Every run now records **where it sits in the design space of its architecture**, in the `param_domains.yml` of its job directory and from there in the meta of its result record (`_point.<variable>`). A record already said which configuration of each parameter domain it ran, which is everything a hand-written configuration is; a configuration a rule produced is more than its name -- it stands for one value of each variable of its domain -- and those values are what a search reasons about. Recovering them afterwards meant asking every point of every domain what it would be called and hoping exactly one answered, which is guesswork over a question the job had the answer to all along. What is written are *coordinates*, one entry per variable, and not the genome a search operates on: a genome is a tuple of indices into the axes of one particular space, and the space a campaign searches is not the one a plain synthesis knows -- it pins the domains a selection fixed, adds an axis for the frequency and another for the toolchain, and renumbers everything when the architecture gains a parameter. Coordinates survive all of it. `odatix fmax`, `odatix custom_freq`, a simulation, a workflow and an exploration all record them, which is the point: a sweep run last month is a hundred designs already measured, and the only thing keeping a search from starting there was that nobody had written down where they were. The keys are `_`-prefixed, so they stay out of what identifies a record, out of the dimensions a chart offers and out of the joins derived metrics run on -- they say where a record is, not what it is
- An exploration now **starts from what the workspace already measured**. A sweep of one parameter, a single `odatix synth`, a simulation, a campaign that was looking for something else: each of those measured designs of the space about to be searched, and each of them is worth exactly as much to the search as a design it would have run itself -- for nothing. They go into the front and into what the strategy learns from before the first batch, and are never run again. Only the results whose run recorded where they sit are taken, so nothing is ever guessed from a configuration name; a result that cannot be placed in the space is read for the front the way it always was, and not for the search. Reused designs do not count against the budget -- it says how many designs the exploration evaluates, and it evaluated none of these -- and are marked as reused in the archive so an exploration started a second time does not count them as its own either. `reuse_results` (yes by default) in the campaign file turns it off, as does `--no-reuse` on the command line; `-o/--overwrite` already means "evaluate again what is already done", and implies it
- `ArchitectureSpace.genome_of()` turns those coordinates back into a place in a space, one lookup per axis. Nothing is inferred: coordinates that name no axis of the space, an axis nothing speaks about, a configuration a selection does not allow, a frequency or a toolchain the exploration does not search, or a design its rules and exclusions take out -- each of them answers *not a design of this space*, and the record stays what it was, a result read for the front and not for the search
- Add `odatix.dse` as a Python API: `explore()` runs the exploration a workspace describes, and `Campaign`, `ArchitectureSpace`, `Objectives` and the strategies are usable on their own — handing a campaign its own evaluator is what lets a search be exercised without synthesizing anything
- Configurations can now be described by what their values have to satisfy, and not only by what values there are: `configurations.constraints` holds boolean expressions over the variables of a domain (`"${p_rf_sp} <= ${p_rf_read_buf}"`, or `expr` with a `message` saying why), written like the `op` of a `function` variable and checked once the derived variables are computed. A combination that does not satisfy every one of them is not a configuration of the domain at all — never named, never counted, never previewed, never run — which is what tells a constraint apart from the configuration blacklist, whose entries exist and are simply not run. Ruling out a combination used to mean working out which names it produced and blacklisting them one by one, a list that had to be recomputed whenever the naming changed; the condition itself no longer goes stale. A search sees the same space a sweep does, so an exploration never proposes a design its constraints reject, and an expression that cannot be evaluated is reported once and rejects everything rather than quietly keeping every point. In the GUI, the constraints of a domain are edited under **Advanced**, next to the two templates, one expression per line, with the configuration count and the preview following them as they are typed
- `ConfigGenerator` now exposes the axes of a space (`dimensions()`), and `ParameterSpace` exposes `axes()`, `size()` and `assignment()` on top of them: what a point is free to choose, and what it may choose there, without walking the cross product. Variables sharing a `group` form one axis rather than one each, which is what keeps a paired couple paired however the space is explored
- Add `exclusions`, in the `_settings.yml` of an architecture: the combinations of its parameter domains that are not part of its design space. A domain could already say which of *its own* combinations mean something (`constraints`), but never anything about the others -- Odatix crosses domains with `+`, so the only way to leave a cross-domain combination out was not to write the sweep line producing it, once per run settings file, in a place no search reads and where nothing says why. An exclusion says it once, next to the design, and everything that walks the space applies it: an `odatix fmax` sweep, a simulation sweep, an `odatix dse` search and the configuration preview of the GUI leave out exactly the same points. Each rule has a `when` (the combination it is about), optionally a `require` (what such a point has to be instead), a `message` and an `id`
- An exclusion is one of three kinds, because they do not mean the same thing. `illegal`: the design does not work, the point does not exist -- asking for it by name is an error, a wildcard simply does not expand to it. `duplicate`: the design works and is the same hardware as another one, a parameter the rest of the configuration makes meaningless; what matters is not to drop it but to pick one, which is what `require` is for, and a search *folds* the other points onto the canonical one instead of throwing them away, so the space keeps its density and the budget is not spent proposing points that do not exist. `dominated`: the design works and is its own, but another beats it on everything a campaign is looking for -- knowledge about a question rather than about a design, so it is not applied unless a campaign asks for it
- A campaign decides which of them its question applies, in the new `exclusions` section of its file: `apply` (`[illegal, duplicate]` by default), `ignore` (the `id` of a rule this campaign does not want -- an area-oriented campaign keeps the design a frequency-oriented one calls dominated) and `rules` of its own. The line printed when an exploration starts says how many combinations are taken out, and the budget is compared against the designs that exist rather than against the number of combinations of the axes
- Exclusions are written in the one expression language Odatix already had, now shared by the domain constraints and everything else (`odatix.lib.expressions`): `$variable` for the main domain, `$domain` for the *name* of the configuration a domain contributes (`$Overlap == 'On'`), `$domain.variable` for a value behind it, `$config` and `$architecture`, plus `match()` on a shell pattern, `matches()` on a regular expression, `contains()`, `defined()` and `math`. A name nothing defines is unknown rather than an error, so one block can be written for a family of architectures that do not all have the same domains, and an expression that cannot be evaluated is reported once and rejects nothing
- Add `attributes`, in the `_settings.yml` of a parameter domain: how to read values off the *name* or the *content* of its configurations, through the named groups of a regular expression, plus `defaults` and `values` written per selector. A generated configuration already carries the variables it was built from, and an exclusion reads them directly; a hand-written one is a file with a name and a content, and yet what tells one pipeline topology from another is exactly what an exclusion needs to read. With `from_name: "EX(?P<stage_EX>\\d+)"`, `$config.stage_EX >= 2` means what it says -- values that read as numbers are compared as numbers
- Add support for user-provided constraint files, read on top of the timing constraint Odatix generates itself: an IO placement `.xdc` for an FPGA board, timing exceptions, a floorplan script. They are declared under a `constraints` key, in the target file of a tool for what depends on the part or the board (globally, or under `target_settings/<target>`) and in the `_settings.yml` of an architecture for what depends on the design. Both add up. A declaration is a file path, a list of them, or a mapping with `files` and a `scope` among `synthesis`, `pnr` and `all`, so a floorplan is not handed to a synthesis tool that has no use for it. The files are copied into each job directory, listed in its `settings.tcl` (`$user_constraints_synthesis`, `$user_constraints_pnr`) and read by the new `odatix_read_user_constraints` tcl procedure, which each tool calls with its own reader (`read_xdc` for Vivado, `read_sdc` for Genus and Design Compiler). They are re-read at every iteration of an fmax search, where the generated constraint file is rewritten whole, and travel from a synthesis job to the `odatix pnr` job that continues it. Wired up for Vivado and for the `dummy` tool; a constraint file that cannot be found or read stops the job rather than running it without its constraints
- Add `odatix pnr`, a place & route job type that starts from a synthesis another run has already completed, possibly with a different eda tool. This is what a Design Compiler + Innovus, Design Compiler + ICC2, Genus + Innovus or Genus + ICC2 integration is: `odatix freq -t design_compiler` then `odatix pnr -t innovus --from-tool design_compiler`. The results land in Odatix Explorer like any other job type
- A tool declares a place & route with the new `pnr_command` / `pnr_steps` keys of `tool.yml`, which get flows, steps, `--until` and resume exactly like the synthesis job types. `innovus` and `icc2` ship as tool definitions to start from (the technology setup remains yours to provide), and the `dummy` tool implements the whole chain so it can be exercised without a licence. The technology script a place & route job sources is the one `script_copy_source` gives its target in the target file of the place & route tool, as for a synthesis. Innovus ships with one for the AMS C35 1.8 V standard cells (`innovus/technology/AMS_c35_1V8/technology_setup.tcl`), with which the flow has been run end to end from a Design Compiler netlist to signoff; a technology script declares its LEF and MMMC setup, its power nets, and optionally its core site, power ring layers, clock tree cells and GDS layer map (`odatix_core_site`, `odatix_ring_layers`, `odatix_cts_buffers` / `odatix_cts_inverters`, `odatix_gds_map`)
- A synthesis feeds a place & route job through three handoff files it writes in its result directory: `netlist.v`, `design.sdc` and `design.sdf` (`$netlist_file`, `$sdc_file` and `$sdf_file` in tcl). The built-in Design Compiler and Genus flows publish theirs under those names with the new `odatix_publish_handoff` procedure; a place & route flow reaches them through `$source_netlist`, `$source_sdc`, `$source_sdf` and `$source_work_path`
- Which synthesis jobs a run starts from is listed in the new `odatix_userconfig/pnr_settings.yml` under `sources`, as `<source_type>/<source_tool>[@<source_flow>]/<target>/<architecture>/<configuration>[@<frequency>MHz]` with `*` accepted at every level. `--from-type`, `--from-tool` and `--from-flow` narrow that selection on the command line
- Place & route jobs run in `work/pnr/<pnr_tool[@flow]>/<synth_tool[@synth_flow]>/<target>/<architecture>/<configuration>/<frequency>`, the last segment being `<N>MHz` for a custom frequency source and `fmax` for an fmax one, so results implemented from different synthesis tools never collide. The synthesis they came from is exported as the `source_type`, `source_tool` and `source_flow` meta keys, and read back from `pnr.yml` by a full re-export
- Add a place & route page to the GUI (Run Jobs -> Run Place & Route): the completed synthesis jobs of the workspace are listed per eda tool that produced them, and the ones whose flow wrote no handoff files are shown as unusable rather than hidden
- Add support for user-defined EDA tools: drop a tool directory (containing a `tool.yml`) in `odatix_userconfig/tools` and Odatix will use it. Tools are now discovered by scanning this directory (searched first) and the built-in `odatix_eda_tools` directory, instead of relying on a hard-coded list of supported tools; a user tool overrides a built-in one with the same name. The tools directory can be changed with the `tools_path` key of the workspace settings file. A new `$tool_path` variable, usable in `tool.yml`, points to the tool's own directory
- Add a `target_file` key to `tool.yml` to set the name of a tool's target definition file (defaults to `target_<tool>.yml`)
- Add support for several flows per eda tool: a flow is a way of running a tool — a different script, different options, sometimes a different binary. Flows are declared in the new `flows` section of `tool.yml`, the commands declared in the `unix`/`windows` sections being those of the tool's default flow (named by the new `default_flow` key). A flow can define its own `metrics_file`, and its own `tool_test_command` when it runs a different binary
- Select a flow with `-f/--flow` (`odatix fmax`, `odatix freq`), or with `-f/--flow <flow>` / `-f/--flow <tool>:<flow>` for `odatix analyze`, which runs several tools at once. Without it, the tool's default flow is used
- Flows of the same tool are alternatives meant to be compared, so each one runs in its own work directory, named `<tool>@<flow>` (`work/custom_freq_synthesis/vivado@power_opt/...`). The default flow keeps the bare tool name, so work directories produced before flows existed keep resolving. All the flows of a tool are still exported into that tool's single results file, told apart by the `flow` meta key, so Odatix Explorer can compare them
- Vivado ships a `power_opt` flow (automatic clock gating at synthesis, then a power optimization pass) alongside its `standard` one; Design Compiler ships a `dcnxt` flow (running `dcnxt_shell`) alongside its `dc_shell` `synthesis` one
- A flow now starts from the default flow's declaration and overrides only what it says: steps are merged by step name (a step of the same name is replaced where it already was, the inherited order is kept, and new steps are appended), so a flow changing only how the design is synthesized declares that one step and inherits the rest; declaring a `<job_type>_command` replaces inherited steps with a single command
- A user `tool.yml` can now add flows to a built-in tool: when a tool is defined both in the workspace tools directory and in the built-in one, the two `tool.yml` files are merged key by key (the workspace one wins), and the tcl scripts of both directories are copied to the work directory. A workspace `tool.yml` holding only a `flows` section therefore extends the built-in tool instead of shadowing it
- The flow a job ran with is recorded in the results file (`flow` meta key) and in the job work directory (`flow.txt`), so a full re-export (`odatix res_synth`) keeps the flow of results produced earlier
- Add support for splitting a job into ordered steps: `<job_type>_steps` (a list of named commands) is declared instead of `<job_type>_command`. Each step runs as its own process, the tool handing its state over through its own checkpoints. Being stepped is a property of what the tool runs, not of a dedicated flow: it is declared in the tool's platform section and every flow inherits it, so any flow can be stopped wherever
- Stop a run at a given step with `-u/--until <step>`; a later run resumes at the first step left to do instead of redoing everything, so a bitstream can be generated only for the implementations worth it, and a job stopped after a checkpoint can be picked back up. `--rerun-from <step>` forces re-running from a given step, `-o/--overwrite` still redoes everything

- A stepped job type can now declare how the eda tool is *opened* rather than a whole command per step: `<job_type>_session` (with `command`, and optionally `begin` and `end`) says how the tool is launched, and each step declares only the `args` it adds to it. The steps of one run then share a **single process** — the tool opens once, runs them all, and exits — instead of being opened and closed once per step. `--until`, `--rerun-from` and resume are unaffected: the session covers exactly the steps the run has left to do, so a run resuming at `pnr` opens one session on `pnr` and `bitstream` alone. Steps declaring their own `command` still get a process each, and the two can be mixed. A flow overriding a session merges it key by key

A custom frequency synthesis carries a design checkpoint from one step to the next, so nothing is synthesized twice. An fmax search reruns the flow at every frequency it probes, so its steps are searches of increasing depth instead: `synthesis` converges on post-synthesis timing (fast and optimistic), `pnr` on post-route timing (what the design really reaches), and `bitstream` implements at the frequency found. A design space can therefore be screened cheaply before implementing the part of it worth it
- Design Compiler splits both its synthesis jobs into steps, for the `dc_shell` and `dcnxt_shell` flows alike. A custom frequency synthesis goes `elaborate` (elaboration, linking and uniquification) / `synthesis` (constraints, compilation and reports, where it stops by default) / `netlist` (Verilog netlist, SDC and SDF published for `odatix pnr`), each step handing its design over to the next through a `.ddc` database instead of reading the RTL again. - Results are exported **once per step** rather than once per job: the `step` a record holds is a dimension of its own, so the same metric measured after synthesis and after place & route is one metric compared across two steps instead of two metrics told apart by their name (`LUT_count_synth` / `LUT_count` are now a single `LUT_count`). - Add derived metrics: metrics a result does not hold itself but gets from another result, which is what links simulation results to synthesis results. - A simulation can also substitute **one set of parameters per configuration** of a domain, and not only the same text for all of them: `param_dir` names a directory of the simulation holding the configurations of that domain, by file (`8bits.txt`, `16bits.txt`, ...) or by rule (a `_settings.yml` with `configurations` and `variables`), exactly like a parameter domain of an architecture, rules resolved on the fly with nothing to generate beforehand. - Such a directory does not have to hold one file per configuration of the domain either: its `_settings.yml` can name **several configurations at once**, under `match`, as `selector: configuration`. A selector is a name, a shell pattern (`"P*"`, `"M?0[01]"`), a regular expression (`"/^M[0-9]{4}$/"`) or a condition on `$name` — the configuration being run — and `$value` — what it substitutes, when that is a single number: `"$value > 7": wide_params`, `"$name > 62": late_params`, `"$value >= 4 and $value < 16": mid_params`. The built-in strategies are declared this way, and a strategy of your own is a few parameters in the `tool.yml` of the workspace

Design Compiler NXT is now a tool of its own, `dc_nxt`, which extends `design_compiler` with one parameter, the binary its commands run (`dcnxt_shell`), and shares its targets. It used to be a flow of Design Compiler, which made the binary and the strategy one choice; as two tools, every strategy exists for both binaries, and an exploration chooses the tool and the strategy independently (`tool: [design_compiler, dc_nxt]`, `flow: [ultra, ultra_area]`)
- The resource guard, which pauses running jobs while the machine is overloaded, can now be turned off: `resource_guard`, `cpu_limit` and `mem_limit` in `odatix.yml` (on, 98 % and 98 % by default). It used to be always on, with no way to change its limits. A session can also be switched while it runs: `a` in the terminal monitor, which shows its state in the header, or `POST /config?resource_guard=false`. Turning the guard off resumes the jobs it had paused. Where it cannot run (`psutil` missing, Windows) the monitors say so instead of showing a switch that silently flips back

- `odatix analyze` reports **findings** instead of error strings: each message of the tool becomes a severity, a category of a vocabulary shared by every tool (missing module, syntax error, latch, width mismatch, multiple drivers...), what it is about, where (`rtl/top.sv:2`), the message id of the tool and the source excerpt it printed. The same RTL is often accepted by one tool and refused by another: the report now says which tool flagged what, side by side. Six statuses: failed, *tool failure* (the tool could not run — no license, missing technology files — which says nothing of the design), incomplete, warnings, *not supported* (a VHDL design given to Verilator is no longer a pile of syntax errors) and passed
- **Expected findings**: what is normal is reported apart, with its reason, and does not count — a design whose findings are all expected passes, so whatever remains deserves attention. Odatix declares what each tool says of every design (the Reset Release IP advice of Quartus, the style remarks of the Verilator lint); the new `expected` section of `analysis_settings.yml` declares what is normal for your designs, by category, code, subject, file, message, tool and architecture
- How the reports of a tool are read is no longer written in Odatix: it is the `analysis.yml` of the tool (Vivado, Quartus, Design Compiler, Genus, Verilator and LibreLane ship one), read on top of the shared `_common/analysis.yml`, and completed or corrected by `<tools_path>/<tool>/analysis.yml` in the workspace, like metrics files. A definition holds message rules (regular expressions with named groups), a table of message ids, what is expected, the languages the tool reads, and can `extend` another one (LibreLane reads like Verilator, plus Yosys)
- Message rules of `analysis.yml` can read what a message says on the lines below it (`after`: Genus names the file, the line and the subject there), the rows of a list under a heading (`heading`: the checks of Genus' `check_design -all`), and write their message themselves from what they captured (`message`, in a rule or in the `codes` table: `"Latch inferred for '{subject}'"`). A `secondary` message is left out when a finding at least as severe is there, not only for errors. The bits of a bus reported one by one are one finding that says them: `Input 'd[15:8]' is never read`
- Add `odatix res_analysis`: the report of the analyses of the work directory, which exports them again (`-e` to only print it)
- The terminal report of an analysis is generic: a status matrix when several tools ran, the kinds of findings by tool, one line per design that needs attention, then the expected findings grouped by reason
- The console output of every synthesis and analysis job is kept in `log/console.log`: a tool failing before writing a log of its own only ever says why there

- Add **simulation templates**: `ghdl`, `verilator`, `questa`, `xsim` and `icarus`, simulations Odatix provides that compile, elaborate and run any design and its testbench with their simulator, nothing in them being specific to a design. A run names one like any simulation (`odatix sim -s questa -a "MyCPU/*"`, or `- questa: [...]` in `sim_settings.yml`), and a simulation starts from one with `template:` and says only what changes — its testbench, the metrics of its testbench. A simulation of the workspace with the name of a template replaces it. Each template refuses, when the run is checked, a design or a testbench written in a language its simulator does not compile, and a simulator that is not in the `PATH`, and reports for every configuration whether it passed, its errors and warnings, its compile, elaboration and simulation times and its simulated cycles per second (`sim_report.yml`)
- Every simulation job is told about the design under test: `odatix_sim.yml` and `odatix_sim.f` in its work directory hold its sources by language and in compilation order (packages first, from what each file defines and uses, or from a `filelist.f` of the design), its top, clock and reset, its testbench and the value of each parameter domain and variable of the configuration. The same values are placeholders of the simulation commands: `${vhdl_files}`, `${sv_files}`, `${tb_top}`, `${reset_signal}`, `${<variable>}`...
- The testbench of a design belongs to its architecture: `testbench` (`top`, `files`, `parameters`) in `architectures/<arch>/_settings.yml`, which every template runs. `parameters` give the testbench top the configuration under test (`WIDTH: ${width}`). A design without a testbench still runs: Odatix generates a minimal one, in the language of the design, which drives its inputs with random values, fails on an output that stays unknown once out of reset and dumps a VCD (`cycles`, `stimulus`, `waves`; `reset_active_low` when the reset's name does not say)
- The Cordic examples are a testbench per language, attached to each architecture, run by templates: the four `TB_Example_Cordic_*` simulations hold no script anymore
- Choose the workflows of a run from the command line, with `-W/--workflow` (`odatix workflow -W "basic/*"`), and from the Python API (`workflows=`), as the other run commands choose their architectures
- A workflow task named after a file can say `phony: No`: it is then skipped once its file exists, which lets a task build an environment once for every job of the run
- `odatix.run` can follow what it started: `Run.status()`, `Run.wait()`, `Run.session`, and `odatix.run.sessions()` / `Session` to list the sessions of a workspace, follow their jobs, pause, resume or kill one, change the number of parallel jobs and stop a session. `odatix.dse.explore()` runs an exploration from a script, in a session of its own
- `ls`, `monitor` and `stop` take `--any-workspace` to reach the sessions of other workspaces

### Changed

#### Odatix

- **Breaking — the command line**, made consistent with the new [glossary](https://odatix.readthedocs.io/docs/glossary/). `odatix --init` becomes `odatix init`, `odatix freq` becomes `odatix synth`, and the `res_*` exports become `odatix results [synth|sim|workflow|analysis|derived]` (`odatix results` alone exports everything). `odatix init -e`, `odatix generate -w`, `odatix clean -f/--force` and `odatix dse -T` become `--examples`, `-p/--workflowpath`, `-y/--yes` and `--target`. The former spellings still work for one version, with a warning saying what to type instead. `odatix synthesis`, `odatix explore`, `odatix res_benchmark` (a benchmark score is a simulation metric) and the `--force` spelling of `--continue-on-error` are gone. `odatix -h` lists the commands by group, and every message is prefixed with its command
- **Breaking — settings files are named after the command that reads them**: `fmax_settings.yml`, `synth_settings.yml`, `sim_settings.yml`, `analyze_settings.yml` and `clean_settings.yml`, pointed to by `fmax_settings_file`, `synth_settings_file`, `sim_settings_file` and `analyze_settings_file` in `odatix.yml`. The `custom_freq_synthesis` block of an architecture becomes `fixed_freq_synthesis`. The former names are still read for one version, with a warning
- Add `odatix migrate`, which rewrites the settings files of a workspace written in a former format -- keys, file names, `fmax_lower_bound`/`fmax_upper_bound`, `generate_configurations`, `disabled_targets` -- keeping their comments and layout and a `.bak` of each. The workspace page of the GUI offers the same
- Add `default_tool` in `odatix.yml`: the tool `odatix fmax`, `synth` and `analyze` run when `-t/--tool` names none (`odatix init` sets it to `vivado`). Without it, a workspace with the target file of a single tool runs that tool
- Add `--target` to `odatix fmax`, `synth` and `pnr`, to run on some of the targets the target file enables
- Add `-a/--architecture` (`--arch`) to `odatix fmax`, `synth` and `analyze`: the architectures to run, written as the entries of `architectures` in the run settings file (`-a "MyCPU/*" "MyCPU + width/16bits"`), replacing that list for one run. `odatix dse -a` takes several values the same way. **Breaking**: `--archpath` loses its short form `-a`, still accepted with a warning by `odatix generate`
- Add `-s/--sim` and `-a/--architecture` to `odatix sim`: the simulations to run, out of those of `sim_settings.yml`, and the architectures to run them on, replacing those the file gives them. **Breaking**: `--simpath` loses its short form `-s`
- `odatix dse -c/--config` names the workspace settings file, as everywhere else; the exploration settings file is given with `-i/--input`
- Packaging: the GUI assets and themes and the eda tool definitions are now in the source distribution, and the data files deeper than one directory in the wheel, whatever the setuptools version

- Resolving a large selection is now around eight times faster. A sweep line crossing several parameter domains stands for the product of everything it names -- a quarter of a million combinations is what six domains of an ordinary processor already amount to -- and every one of them was checked against the exclusions of its architecture by normalizing, compiling and evaluating the same handful of expressions again from their text, and by reading the name and the whole file of a configuration again for every combination it appeared in. Expressions are now compiled once and evaluated against the values of a point without an environment being built for the occasion, and what a configuration is worth is read once per configuration instead of once per point. Nothing about what a selection expands to changes, exclusions included
- What a sweep leaves out is now said once per rule rather than once per combination: a wildcard over six parameter domains was answered with seventy thousand notes, which is not an explanation but a way of hiding one. Each rule that took something out is worth one note, how many combinations it took and one of them as an example. Asking for a combination by name is still an error naming that combination
- A selection standing for more than a hundred entries is left in the order its wildcards produced it, instead of being sorted by natural order. Natural order is what puts "8bits" before "16bits", and it is worth what it costs on the handful of entries a run names; on a design space it is not, the entries already coming out in that order -- every wildcard is resolved in natural order, and the product of the domains preserves it

- **Security**: a daemon session is now private to the user who owns it, and every request to it is authenticated. Enqueuing a job runs a command line on the machine hosting the session, so an API anyone could reach was an API anyone could run commands through — which, with a session listening on a TCP port for every user of the machine and, if the port was reachable, for the network, is what it was. A session now listens on a **unix domain socket** in a directory only its owner may enter (Windows, whose ASGI server cannot serve one, falls back to a loopback TCP port), and it generates two random tokens at startup: a **control** token for everything that acts (enqueue, start, pause, kill, configure, shut down) and a **read** token for snapshots and logs, so watching a session can be handed over without handing over the right to run code. The tokens live in the session's state file, created readable by its owner alone; Odatix commands and the GUI read them from there, so nothing changes in day-to-day use. The `Host` header of every request is checked too, which is what stops a web page you visit from being used to reach a session on `127.0.0.1`. A session refuses to bind a non-loopback address unless explicitly told to
- Sessions on another machine are reached with the new `-R`/`--remote` option of `odatix ls`, `odatix monitor` and `odatix stop` (`odatix monitor -R user@server -S nightly`), through an **SSH tunnel to the remote session's socket**: no port is opened anywhere, authentication and encryption are SSH's, and the session token authorises the calls inside the tunnel. `user@server:/path/to/workspace` selects a workspace on the other side. `odatix ls --json` prints the session list a remote Odatix reads over that connection
- `odatix ls`, and the session lists of the GUI, now show one `address` column in place of `host` and `port`, since a session on a unix socket has neither. An explicit endpoint (`--host`/`--port`) takes the session token with `--token` or from `$ODATIX_DAEMON_TOKEN`
- A job of the daemon now carries the rules its progress is read with, instead of the daemon holding one set of rules for everything it runs. A session running the jobs of two commands at once no longer reads the progress of one with the rules of the other
- Adding jobs to a daemon session and telling that session how to run them are now two separate things: a caller that only wants its jobs run leaves the session configured as it found it
- A parameter domain sweeping a single variable no longer has to write its `configurations` block: declaring the variable says everything, and its configurations are named after its values and hold them (`name` and `template` both default to `${the variable}`). Either can still be written to say something else, and with more than one variable both are still required, since how the values are combined and written cannot be guessed. This holds for a named parameter domain only: at the root of an architecture or of a workflow the same variables may be substituted into its commands instead. In the GUI, both fields of such a domain stay empty and show what Odatix uses in their place; a template that says nothing is no longer written to file
- Rename `-f/--force` (continue fmax synthesis on synthesis error) to `--continue-on-error`, freeing `-f` for `--flow`. The long form `--force` is still accepted
- What an architecture says for a part of its jobs only is now declared in an `overrides` section of its `_settings.yml`: an ordered list of rules, each saying which jobs it applies to and what those jobs use instead. A rule selects on the tool (`tools: vivado` for every flow of it, `tools: vivado@power_opt` for one), the target (`targets:`) and the configuration (`configurations:`), each taking one name, a list of names or shell-style patterns (`xc7a*`), and an axis a rule does not name it does not restrict. It can hold any key of the file, not just fmax bounds, custom frequencies and constraints. Rules apply in order on top of the top level of the file: the last one matching a job has the last word on the keys it names — except `constraints`, which add up, and a frequency `list` asking for `list_append`. This replaces the settings that used to be declared at the root of the file under a target's own name, then in a `targets` section: a constraint file no longer has to name the stage that reads it through the tool it belongs to, since the rule declaring it already says which jobs read it. This is a breaking change with no backward compatibility: an architecture still declaring per target settings the old way runs with its global settings instead, and its per target bounds and constraints are silently ignored. The example architectures ship migrated. The section is editable from the GUI, in the Architecture Editor: one card per rule, with its selectors, its fmax bounds, its custom frequencies and its constraint files
- Constraint files are editable from the GUI: the Architecture Editor writes both the `constraints` of the architecture and those of one of its targets, one file per line, a file only one stage reads being followed by `@ synthesis` or `@ pnr`
- What a simulation substitutes for an architecture is now edited where every other set of configurations is: the **configuration editor**, opened on `?sim=<simulation>&arch=<architecture>` by the *Edit parameter domains* button of the architecture card of the Simulation Editor. One section per parameter domain the simulation overrides, holding what it points at (the directory of configurations, the default parameter file, whether the architecture's own replacement still applies), how its values are written, the configurations themselves and the preview of the file they are written into — the same page, the same cards, the same rules as a parameter domain of an architecture, instead of a form of its own in the Simulation Editor. The card of an architecture now says how many domains it overrides and opens them, and carries what it does not edit untouched
- Where a `param_domains` entry of a simulation names a `param_dir`, that directory now says how its parameters are written, in its own `_settings.yml` (`use_parameters`, `param_target_file`, `start_delimiter`, `stop_delimiter`), exactly like a parameter domain of an architecture says it — the entry keeping only what points at it. The same keys written in the entry are still read, and still win, so nothing written before this stops working
- A `param_domains` entry of a simulation now holds the **list** of the replacements one parameter domain triggers, instead of a single one. One value has consequences in as many files as it takes — the testbench reads it, the Makefile building the testbench passes it on, a wrapper declares it — and each of them is one item of the list, with its own `param_target_file`, delimiters and parameters, everything unsaid still inherited from the architecture's domain. Written nowhere, `combine` now follows the place in the list: the first replacement takes the architecture's place and the ones after it are added, so a list is read the way it looks. A domain replaced in a single place is still written as that replacement itself, without the list, so nothing that describes one replacement per domain changes. This replaces the former syntax entirely: a domain used to be one mapping, and YAML has no second key of the same name, so asking for two replacements of the same domain silently kept one. In the configuration editor, one section is one replacement, and a domain shown twice is a domain replaced twice
- How a design space is described is unified: a settings file now says how its configurations are built in a single `configurations` block (`name` and `template`), next to the `variables` at the root of the file. The `generate_configurations` flag and its `generate_configurations_settings` block are gone from the files Odatix writes — describing configurations is what asks for them. Files written the former way keep working exactly as they did: they are read, and saved in the new form the next time Odatix writes them, so no file has to be migrated by hand. The shipped examples and the documentation use the new form
- Generating configurations is no longer a step to run before anything else: a run resolves what the rules of a domain describe on its own, so `odatix generate` is optional. Configuration files written by hand still work as they always did, and a file always wins over what a rule would produce, which is how a single configuration is corrected without giving up the rules. A configuration a run resolves is written under `.odatix_configs/` inside the domain, never among the files the user keeps; deleting that directory is always safe
- `odatix generate` now writes the configurations out for the workspaces that would rather keep them as files, and records what it wrote in a `.odatix_generated.yml` manifest next to them. A configuration edited by hand after being generated is **kept** by a later `odatix generate` instead of being silently overwritten; `-o` takes it back to what its rule says. The new `-C/--clean` deletes what an earlier generation wrote and the rules no longer describe — never a file written by hand. Generating twice is now a no-op that succeeds, where it used to fail with "everything already exists". The manifest is written by `odatix generate` and by nothing else: a workspace that never runs it never has one, and deleting it is safe
- The Configuration Generator page is gone, and what it did is part of the configuration editor: every parameter domain carries a **Configuration rules** panel, folded away until opened, holding the name template, the content template and the variables of that domain, with the values of each variable previewed as they are edited. Saving the rules re-reads the configurations of that domain alone, so what a rule produces appears among them straight away. The configurations of a domain are now what it resolves to rather than the files it holds: one that only a rule describes gets a card like any other, labelled *generated* (or *edited*, when a file of that name says something else), and the strip above them counts what the domain holds and where it comes from. A configuration a rule produces cannot be renamed in place, its name being the name template, and deleting an *edited* one takes it back to what its rule says instead of removing it. The `/config_generator` route still leads to the domain it named, so a bookmark or an `odatix-gui config_generator` invocation lands where it used to
- The two templates of a **Configuration rules** panel highlight their `${...}` variables, in the colors the command fields of the other editors use: a variable of that domain reads as defined, anything else is flagged as not defined here. Each panel only sees the variables of its own domain, so two domains declaring the same name do not colour each other's templates
- While the rules of a domain differ from what its settings file says, the configurations they would produce are previewed above the ones the domain holds: the same grid and the same cards as the list they will join, dashed and quiet, each holding a *preview* chip where a saved one holds its origin. The strip above the list says how many the rules describe and that they are not saved yet, and the counters of the domain are centered over the cards they count
- The `addr` and `data` parameter domains of the `Example_Rom_Chisel` example no longer ship configuration files: their rules describe them, as the example is meant to show. The files that were committed there had been generated from an earlier version of the `addr` rules and no longer matched them, which — now that a run resolves what the rules describe — would have made that domain sweep eleven configurations instead of seven
- Two points of a design space can no longer be given the same name: a name template leaving out a variable used to make configurations silently collapse into one, losing points from the sweep without any signal. It is now reported, naming the assignments that collide
- Variables are now declared under `variables`, at the **root** of a `_settings.yml`, instead of under `generate_configurations_settings.variables`. They are no longer specific to configuration generation: the same block generates configurations, sweeps a workflow, and sweeps an architecture whose RTL is generated (virtual parameter domains), while `generate_configurations_settings` keeps only what generation needs (`template` and `name`). Settings files declaring variables the former way keep working: Odatix reads them there when the root key is absent, and writes them at the root the next time it saves the file. The Python API follows: `set_variable()`, `remove_variable()` and `variable_names()` are now on the settings of an architecture, of a workflow and of a parameter domain (`architecture.settings.set_variable(...)`) rather than on its generation block
- Synthesis result records now carry the eda tool they were produced with (`tool` meta key), alongside the new `flow` key
- Results are now exported in the v2 format (`schema: 2`, flat `results` records); parameter domains are flattened into each record's `meta`
- Factor the file-value parsers (regex/csv/yaml/json), numeric conversion, operation evaluation and existing-results loading shared by synthesis and workflow result export into a single `export_common` module (the `error_if_missing` flag is now consistently honored across all of them)
- Replace `odatix.components.workspace` (a flat set of helpers taking a path as first argument) with the `odatix.workspace` package. Every page of the graphical interface now goes through it, so a workspace is opened once and no path is passed around anymore
- Every run now goes through `odatix.run`, whether a command, the graphical interface or a script starts it. The "Run jobs" page had one check function per job type, each repeating the same twenty arguments; it now has one, and the run it builds carries its own state from the check phase to the preparation instead of a tuple kept in a module global
- Deciding what a run does with a job directory it already has (cached, resumed, owned by another daemon session, to be overwritten) is now `odatix.run.JobPlanner`, taken out of `ArchitectureHandler` since it is the same decision for every job type
- The most specific frequency `list` of an architecture now wins over the more general ones, as the per-target and per-configuration overrides already did for every other setting: a `list` set for one configuration used to be silently replaced by the file-wide one. `list_append` keeps its meaning — add to the list of the level above instead of replacing it
- An architecture whose settings file says `file_copy_enable: No` no longer requires `file_copy_source` and `file_copy_dest` to be there too
- The default flow of Design Compiler is now called `standard` (it was `dc_shell`), and its `dcnxt_shell` flow is now the `dc_nxt` tool. Results exported earlier keep the flow name they were exported with
- The options several commands share are declared once (`odatix.components.cli_options`), with the same flags, destination and help everywhere, and a run command turns its command line into run options in one call (`RunOptions.from_namespace`) instead of copying each option by hand. Commands are dispatched through a table rather than by comparing names, one of those comparisons being a substring test that only worked by accident
- `-f/--format` is removed from `odatix results` and `odatix res_synth`: results are only ever written as v2 YAML, and the option changed nothing
- `-w/--work` is removed from `odatix dse`: nothing read it
- `odatix sim` accepts `-e/--noexport`, like the other run commands
- `odatix replace` now fails when its delimiters match nothing: the output it writes is then a mere copy of the input
- `odatix analyze` runs through `odatix.run` and the daemon like every other run command, and gains `-d/--detach` and `-S/--session`: it used to run its jobs itself in a monitor of its own, so they could neither be detached nor followed from the GUI. Its jobs are prepared like those of a synthesis, and the analysis summary file written in the work directory (`analysis.yml`) is gone: the results file and `odatix res_analysis` hold the same
- Analysis records (`results_analysis_<tool>.yml`) hold `_findings`, `_summary`, `_languages` and `_logs`, statuses are written in lower case, and the metrics are `error_count`, `critical_warning_count`, `warning_count`, `info_count` and `expected_count`. Records written by earlier versions are still read
- The Verilator analysis lints for real (`--lint-only -Wall -Wno-fatal`): it did not report unused or undriven signals, and any warning — a latch — failed the analysis
- The RTL Analysis page of Explorer shows the findings of each design (category, message, location, message id, source excerpt) with what needs attention first and the expected findings folded apart, the kinds of findings by tool (clicking one keeps the designs it was reported for), and the new statuses
- The workflow and simulation editors share their task cards (`odatix.gui.task_editor`), as they already shared their variable cards
- `report_path` is no longer a key of `tool.yml`, nor a field of the GUI tool editor: it was read and never used, a job's reports always being in its `report` directory (`$report_path`). A `tool.yml` still holding it is read as before, and the key is dropped the next time it is saved. `rtl_file_format`, which nothing ever read, is removed from the configuration generation example
- Sessions belong to their workspace: `odatix ls`, `monitor`, `stop` and `-S` only see the sessions of the current workspace (`odatix ls` says how many exist elsewhere), and `stop --all` no longer stops the sessions of every workspace of the user
- `-E/--exit` also closes the session once all its jobs are over, after printing how many succeeded and failed: every run used to leave an idle session behind for good

- The steps of a `Run` of the Python API run from the root of its workspace, whatever the current directory of the script, and print no color codes when the output is not a terminal
- The "Force single threading" switch is removed from the run jobs page: it had no effect, the setting being one of the target file

- An fmax search on Design Compiler no longer lets one iteration leak into the next. Each iteration elaborated the RTL again on top of what the previous one left in memory, and only the top module was elaborated anew: its submodules were linked as the previous iteration had **compiled** them, at another frequency. What an iteration found depended on the ones before it — on `Example_ALU_sv` 32 bits (`standard`, AMS C35), the search reported 59 MHz where a synthesis on its own meets timing at 67 MHz. The design is now elaborated once, at the first iteration, and every iteration starts again from that database (`remove_design -all`, `read_ddc`), so only the constraints, the compilation and the reports are replayed. - Fix the Vivado `power_opt` flow doing nothing different from `standard` in a custom frequency synthesis: its knobs were only read by the script of an fmax search, while the `synthesis` step ran its own copy of the synthesis commands
- Fix a daemon session grinding to a halt over a long run, which is what an exploration is: nothing ever leaves the job list of a session, so the scheduler carried every job it had ever run, and the two `job in list` tests it made for each of them on every tick made it quadratic in that number -- with the handler lock held throughout, so nothing else could be answered while it ran. At three thousand jobs, a tick spent thirty milliseconds on those tests alone every hundred milliseconds; a few thousand more and the lock was never free. The two lists are now mirrored by sets, which is a hundred and seventy times faster at that size and does not get worse
- Fix a session becoming unreachable rather than merely busy: every endpoint was declared `async` while calling straight into the handler, so a request waiting on the handler lock blocked the event loop, and with it every other client of the session -- the monitor, the GUI, and the exploration polling for its jobs. A session used to export the results of every job that finishes with the scheduler lock held, which kept it silent for a few seconds each time (fixed below), so the probe failed precisely when jobs were completing. Discovery now retries before concluding, and gives a session long enough to finish an export
- Fix the state file of a live session being deleted when it missed one of those probes, which is how a session became permanently invisible: it went on running its jobs with nothing able to find it again, neither to follow it nor to stop it. This is what made a session look dead often enough to be dropped from the listing, and then to lose its state file. Exports now run on their own thread, still one at a time so they cannot race over the results file they share, while the scheduler goes straight back to running jobs. Whether a session answered is now told apart from what it answered: a listing that failed is waited out, said in the log, and gives up with a reason after five minutes rather than either concluding or polling forever
