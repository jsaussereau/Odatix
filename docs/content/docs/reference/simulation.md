# `simulations/<sim>/_settings.yml`

A **simulation** is a directory under `sim_path` (default
`odatix_userconfig/simulations/`) holding a testbench and everything needed to
run it. The whole directory is copied into each job's work directory, next to
the RTL of the configuration under test.

{{< code lang=text filename="A simulation directory" >}}
odatix_userconfig/simulations/TB_Example_Counter_GHDL/
├── _settings.yml    # this page — optional
├── _metrics.yml     # what to extract — optional
├── Makefile         # the default entry point: "make sim"
└── tb/              # testbench sources
{{< /code >}}

`_settings.yml` is **optional**. Without it, the architecture's own settings are
used and Odatix runs `make sim` from the simulation's `Makefile`.

A simulation does not have to be written from scratch: Odatix provides a
[template](#templates) for each common simulator, which a simulation can start
from, or which a run can name directly.

{{< toc >}}

## What the simulation runs

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `tasks` | list | No | Task graph run by the workflow engine. Without it, Odatix runs `make sim`, which then requires a `Makefile`. |

Task entries take exactly the same keys as a
[workflow's](/docs/reference/workflow/#task-entries): `name`, `commands`,
`on_failure_commands`, `dependencies`, `path`, `platforms`. Execution always starts at the task named
**`main`**.

{{< code lang=yaml filename="_settings.yml" >}}
tasks:
  - name: analyze
    commands:
      - ghdl -a ${vhdl_files} ${tb_files}

  - name: main
    dependencies:
      - analyze
    commands:
      - ghdl -e tb_counter
      - ghdl -r tb_counter --stop-time=500ns --vcd=${log_path}/counter.vcd
{{< /code >}}

The job succeeds when every task does. A task fails as soon as one of its
commands exits with an error, and the tasks depending on it do not run: a
command piped into another one (`| tee`) only fails when the last one does.

A simulation that succeeded is not run again: `-o` runs it again. One that
failed, or was stopped, runs again at the next `odatix sim`, from a new work
directory, or in its existing one with `-r`.

### Placeholders available in commands

| Placeholder | Value |
|-------------|-------|
| `${simulation}` | Name of this simulation. |
| `${architecture}` | Design under test. |
| `${configuration}` | Configuration under test. |
| `${arch_full}` | Full name of the variant, domains included. |
| `${top_level_module}` | Top-level module of the design. |
| `${clock_signal}` | Its clock signal. |
| `${reset_signal}` | Its reset signal. |
| `${languages}` | Languages the design is written in (`vhdl`, `verilog`, `sv`), space separated. |
| `${vhdl_files}` | VHDL sources of the design, in [compilation order](#compilation-order). |
| `${verilog_files}` | Verilog sources of the design, in compilation order. |
| `${sv_files}` | SystemVerilog sources of the design, in compilation order. |
| `${include_dirs}` | Directories holding its Verilog headers (`.vh`, `.svh`). |
| `${tb_top}` | Top of the [testbench](#testbench). |
| `${tb_files}` | Sources of the testbench, in compilation order. |
| `${python}` | The Python interpreter running Odatix. |
| `${work_path}` | The simulation's work directory. |
| `${rtl_path}` | Directory holding the copied RTL. |
| `${log_path}` | Directory for the logs, relative to the work directory. Odatix creates it before the first task. |
| `${script_path}` | The simulation's script directory. |
| `${sim_path}` | This simulation's definition directory. |
| `${design_path}` | Source directory of the design under test. |
| `${odatix_path}` | Odatix installation directory. |
| `${<domain>}` | One placeholder per parameter domain of the design under test. |

`${rtl_dir}`, `${log_dir}` and `${odatix_dir}` are the former names of
`${rtl_path}`, `${log_path}` and `${odatix_path}`. They still work, but the new
ones match the variables of the [EDA tools](/docs/reference/tools/) and are what
the editors offer.

File lists are relative to the work directory and separated by spaces. When the
RTL is generated by the job (`generate_rtl`), its files only exist once the job
has started: the `${*_files}` placeholders are then empty, and
[`odatix_sim.yml`](#what-odatix-tells-the-simulation) is the place to read them
from.

## Testbench

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `testbench.top` | string | No | Module or entity at the top of the testbench. |
| `testbench.files` | path or list | No | Its sources, relative to the simulation directory. Glob patterns are accepted. |
| `testbench.parameters` | mapping | No | Parameters (generics) given to the top of the testbench. Values may use the [placeholders](#placeholders-available-in-commands). Read by the [templates](#templates). |
| `testbench.cycles` | int | No | Cycles the [generated testbench](#generated-testbench) runs. Default 1000. |
| `testbench.stimulus` | string | No | What it drives the inputs with: `random` (default) or `zero`. |
| `testbench.waves` | bool | No | Whether it dumps a VCD, `odatix_sim.vcd`. Default `Yes`. |

{{< code lang=yaml filename="_settings.yml" >}}
testbench:
  top: tb_cordic
  files: [tb/tb_cordic.sv]
  parameters:
    WIDTH: ${width}
    ITERATIONS: ${iterations}
{{< /code >}}

Without `top`, Odatix takes `tb_<top_level_module>` when the testbench defines
it, otherwise the only module or entity no other one instantiates.

The testbench a job runs is, by priority:

1. the `files` the simulation names here;
2. the [testbench of the architecture](/docs/reference/architecture/#testbench),
   copied into the job's `testbench/` directory: this is how a
   [template](#templates) runs any design with no simulation of its own;
3. every HDL file of the simulation's `tb/` directory;
4. when there is none, a [generated testbench](#generated-testbench).

`parameters` go with the testbench chosen.

### Generated testbench

A design without a testbench still runs with a [template](#templates): Odatix
generates a minimal one when the job starts, once the RTL exists, in the
language of the top of the design (VHDL for a VHDL entity, SystemVerilog
otherwise). It does not check what the design computes. It:

- instantiates the design, generates its clock and applies its reset;
- drives the inputs with random values (or zeros, `stimulus: zero`) for
  `cycles` cycles;
- dumps a VCD, `odatix_sim.vcd`, which gives a realistic activity to estimate
  the power from;
- fails the simulation when an output is unknown (X) once out of reset, or when
  an assertion of the design fires.

That covers compiling, elaborating and the speed of the simulator on every
configuration. The header of the top is copied as written: its parameters
(which already hold the values of the configuration) become local parameters,
its ports signals, and the packages it imports are imported, so a width like
`[WIDTH-1:0]` stays valid without being evaluated.

The reset is active high unless its name says otherwise (`rst_n`, `resetn`,
`nreset`), or the architecture says so with `reset_active_low`.

What it cannot handle (an interface port, a Verilog header listing only port
names, a type parameter, an unconstrained VHDL port) fails the simulation with
a message saying so: give the design a [testbench of its
own](/docs/reference/architecture/#testbench) then.

The options can be given by the architecture, for every simulation, or by a
simulation:

{{< code lang=yaml filename="architectures/MyCPU/_settings.yml" >}}
testbench:
  cycles: 10000
  stimulus: random
  waves: No
{{< /code >}}

## What Odatix tells the simulation

Before running a job, Odatix writes two files into its work directory, once the
parameters of the configuration are written into the RTL:

- **`odatix_sim.yml`**: the design under test (top, clock, reset, languages),
  its sources by language in compilation order, the testbench (top, files) and
  the value of each parameter domain;
- **`odatix_sim.f`**: the same sources as a plain filelist, design first, then
  testbench, which most simulators read with `-f`.

{{< code lang=yaml filename="odatix_sim.yml" >}}
simulation: TB_Example_Cordic_QuestaSim
architecture: Example_Cordic_vhdl
configuration: Example_Cordic_vhdl
arch_full: Example_Cordic_vhdl+iterations/12+width/8
dut:
  top: cordic
  clock: clock
  reset: reset
  languages: [vhdl]
  rtl_dir: rtl
  rtl_generated: false
sources:
  vhdl: [rtl/cordic.vhdl]
  verilog: []
  sv: []
  include_dirs: []
  order: dependencies
testbench:
  top: tb_cordic
  files: [tb/tb_cordic.sv]
  languages: [sv]
param_domains:
  iterations: '12'
  width: '8'
{{< /code >}}

A testbench reading the parameters of the configuration from this file, or from
the `${<domain>}` placeholders, does not have to parse the RTL.

When the RTL is generated by the job, both files are written again right after
the generation command.

### Compilation order

VHDL needs a package compiled before the units using it, and SystemVerilog a
package before the files importing it. Odatix orders the sources as follows:

1. a **`filelist.f`** at the root of the design's RTL: its order is kept as
   written. It holds one file per line, relative to its own directory, and may
   use `+incdir+`, `-f` and environment variables;
2. otherwise, an order **computed from the sources**: what each file defines
   (entities, packages, contexts, configurations; SystemVerilog packages) and
   what it uses (`use work.pkg`, `entity work.x`, the entity of an architecture,
   the package of a body; `import pkg::*`). Files that depend on nothing keep
   the order of the directory.

## Progress reporting

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `progress.file` | path | `log/progress.log` | File the run writes its progress to, relative to the run directory. |
| `progress.regex` | regex | `(.*): ([0-9]+)%(.*)` | Pattern the percentage is read from. |

{{< code lang=yaml filename="_settings.yml" >}}
progress:
  file: "log/progress.log"
  regex: "(.*): ([0-9]+)%(.*)"
{{< /code >}}

The value feeds the progress bar of the [Job Monitor](/docs/sessions/gui_monitor/).

## Architectures

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `architectures` | list | No | The architectures this simulation runs on, and what it changes for each of them. |

A testbench is written for a design, or for a handful of designs sharing an
interface. Which ones they are is the `architectures` block, and an architecture
with nothing to change is written as its bare name:

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv
  - Example_Cordic_vhdl
{{< /code >}}

Listing an architecture is an **indication, not a restriction**. Running the
simulation on one it does not list works exactly as before, and only prints a
warning:

{{< code lang=text >}}
[simulation_handler.py] warning: "Example_Counter_vhdl" is not one of the architectures "TB_Example_Cordic_GHDL" runs on
{{< /code >}}

An empty list, or no key at all, means the simulation lists nothing: it runs on
the architectures the run names without any warning, and the GUI offers none
until you add one.

An architecture that needs something done differently holds it under its name:

| Key | Type | Description |
|-----|------|-------------|
| `architectures.<architecture>.param_domains` | mapping | How the configuration values are substituted for this architecture, one list of substitutions per domain (see below). |
| `architectures.<architecture>.metrics_file` | path | Metrics file to extract this architecture's runs with, instead of `_metrics.yml`. |

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.sv"
      metrics_file: "_metrics_sv.yml"

  - Example_Cordic_vhdl:
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.vhdl"
{{< /code >}}

Names accept wildcards, `"*"` standing for every architecture, and every entry
matching the design under test applies, in the order they are written — so a
specific architecture placed **after** a wildcard refines it instead of being
shadowed by it:

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - "*":
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.sv"
  - Example_Cordic_vhdl:
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.vhdl"
{{< /code >}}

### Parameters

A simulation inherits the design's parameter replacement: every [parameter
domain](/docs/configurations/) of the configuration is spliced into the design
before the testbench runs. `param_domains` adjusts that for one architecture —
the testbench often needs the same value the design got, but in a file of its
own.

The value of a domain is the **list of the replacements** it triggers: one value
often has consequences in more than one file — the testbench reads it, the
Makefile building the testbench passes it on, a wrapper declares it — and each
of them is one item of the list, with its own target file, delimiters and
parameters.

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `use_parameters` | bool | No | Disable (or re-enable) the replacement. |
| `param_target_file` | path | No | File the replacement is applied to, instead of the design's. |
| `start_delimiter` / `stop_delimiter` | string | No | Markers of the replaced block. |
| `param_file` | path | No | Parameter file, relative to the simulation directory, used whichever configuration of the domain runs, or, along `param_dir`, the default of the configurations it does not describe. |
| `param_dir` | path | No | Directory of the simulation holding **one parameter file per configuration** of the domain, or naming several of them at once with [selectors](#naming-several-configurations-at-once). |
| `combine` | `replace` \| `both` | No | Whether the architecture's own replacement for this domain is dropped in favour of this one, or still applied as well. Unwritten, the first item of the list replaces it and the ones after it are added. |

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          - param_target_file: "tb/tb_cordic.sv"   # the value the testbench reads
          - param_target_file: "Makefile"          # and the one its Makefile passes on
            start_delimiter:   "# ODATIX PARAMS START"
            stop_delimiter:    "# ODATIX PARAMS STOP"
            param_dir:         "make_params/width"
{{< /code >}}

A domain replaced in a single place may be written as that replacement itself,
without the list — the shorter form of a list of one:

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.sv"
{{< /code >}}

Every key is optional: what is not listed is inherited from the domain's own
settings in the architecture. Domain names match the directories under the
architecture (`width/`, `iterations/`, …).

Where a replacement names a `param_dir`, that directory says how its parameters
are written, in its own `_settings.yml` — `use_parameters`, `param_target_file`,
`start_delimiter` and `stop_delimiter`, exactly like a parameter domain of an
architecture says them. The replacement then holds only what points at it
(`param_dir`, `param_file`, `combine`). The same keys written next to it are
still read, and still win.

#### Per-configuration parameters

`param_file` writes the same text whichever configuration of the domain runs.
`param_dir` writes one per configuration instead: it names a directory of the
simulation holding the configurations of that domain, **by file or by rule**,
exactly like a [parameter domain](/docs/configurations/param_domains/) of an
architecture — `<value>.txt` files, a `_settings.yml` declaring
`configurations` and `variables`, or both. The configuration the architecture
runs is the one looked up there, and a rule is resolved on the fly, so nothing
has to be generated beforehand.

Both together make `param_file` the **default** of the domain: the directory is
looked up first, and the configurations it does not describe fall back to the
file instead of being an error.

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          param_dir: "tb_params/width"          # tb_params/width/8bits.txt, 16bits.txt, ...
{{< /code >}}

{{< code lang=yaml filename="tb_params/width/_settings.yml" >}}
param_target_file: "tb/tb_cordic.sv"

configurations:
  name: "${width}bits"
  template: "localparam TB_WIDTH = ${width};"

variables:
  width:
    type: range
    settings: {from: 8, to: 64, step: 8}
{{< /code >}}

These directories are edited like any other configurations: *Edit parameter
domains*, on the architecture card of the simulation editor, opens the
[configuration editor](/docs/gui/app/) on what this simulation substitutes for
that architecture — one section per domain, holding what it points at, how its
values are written, and the configurations themselves, preview included.

#### Naming several configurations at once

A directory does not have to hold one file per configuration of the domain. Its
`_settings.yml` may name **several configurations at once**, under `match`, as
`selector: configuration` — a testbench usually has one set of parameters for a
whole family of designs, and writing that family out one identical file per
member is copying the same thing many times.

{{< code lang=yaml filename="make_params/_settings.yml" >}}
param_target_file: "Makefile"
start_delimiter: "# ODATIX PARAMS START"
stop_delimiter:  "# ODATIX PARAMS STOP"

match:
  "P*":            small_params    # every configuration whose name starts with "P"
  "$value > 7":    wide_params     # every configuration whose value is above 7
  "/^M[0-9]{4}$/": riscv_params    # every configuration whose name matches the regex
  "*":             default_params  # everything else
{{< /code >}}

Four kinds of selectors, told apart by how they are written:

| Selector | Matches |
|----------|---------|
| `small` | that configuration, and no other |
| `P*`, `M?0[01]` | the names this pattern matches (`*`, `?` and `[...]`, as a shell glob) |
| `/^M[0-9]+$/` | the names this regular expression matches (unanchored: `/^P/` and `/P/` differ) |
| `$value > 7`, `$name == 'P8'` | the configurations satisfying this condition |

A condition reads two values:

- `$name` — the name of the configuration being run (`P8`, `M0000`);
- `$value` — what that configuration substitutes, **when it is a single
  number**. A configuration writing several parameters, or something that is not
  a number, has no `$value`, and a condition reading it simply matches nothing.

Both compare as numbers when both sides are numbers, and as text otherwise, so
`$name > 62` and `$name == 'P8'` both say what they look like they say. The
usual operators are available (`==`, `!=`, `<`, `<=`, `>`, `>=`, `and`, `or`,
`not`, parentheses), as in `$value >= 4 and $value < 16`.

A configuration the directory holds **under its own name** — as a file or as one
its rules describe — is always used as it is: selectors only answer for the ones
left. When several of them match, the most specific wins (a name over a pattern,
a pattern over `*`), and the first one written breaks a tie — so the narrow
selectors are written above the broad ones, and a `*` stays the fallback
wherever it sits. A `param_file` written next to the `param_dir` is still the
last resort, for the configurations no selector answers for either.

Selectors are edited under *Matching*, in the section of the domain of the
[configuration editor](/docs/gui/app/): one `selector -> configuration` per
line, with the values and the wildcards highlighted, and a line saying how many
of them point at a configuration this directory does not hold.

#### One replacement, or both

A domain of the architecture already replaces something somewhere — a block of
the design's source. What a simulation writes under the same domain name
**takes its place** by default: only the replacement described here is applied,
which is what you want when the value has moved to a file of the testbench.

`combine: both` keeps the architecture's replacement *and* applies the one
described here as a second replacement: the same domain written into the design
**and** into the testbench, each with its own target file, delimiters and
parameters. Anything the replacement does not say is inherited from the
architecture's domain, so a second target file is often all it takes.

Written nowhere, `combine` follows the place in the list: the **first**
replacement takes the architecture's place, the ones **after** it are added. A
list is therefore read the way it looks — every item is a replacement that
happens — and `combine` is only written to depart from it, `both` on the first
item to keep the design's own replacement alongside.

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          - combine: both                        # the design keeps its own replacement
            param_dir: "tb_params/width"         # and the testbench gets one too,
                                                 # written where that directory says
{{< /code >}}

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Cordic_sv:
      param_domains:
        width:
          param_target_file: "tb/tb_cordic.sv"   # same value, applied to the testbench
        iterations:
          use_parameters: No                     # testbench does not care about this one
{{< /code >}}

#### Simulation-only domains

A name that matches **no** domain of the architecture declares replacements of
the simulation's own. Use it for values only the testbench cares about — a run
length, a seed, a verbosity level. `param_file` (or `param_dir`, with
`domain_value` naming the configuration to run), `start_delimiter` and
`stop_delimiter` are then required, since there is nothing to inherit them from.

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Counter_vhdl:
      param_domains:
        sim_config:
          param_file:        "sim_params.txt"
          param_target_file: "tb/tb_counter.vhdl"
          start_delimiter:   "-- <sim>"
          stop_delimiter:    "-- </sim>"
{{< /code >}}

#### The configuration itself: `__main__`

`__main__` names the replacement of the architecture's configuration (the
`08bits` of `Example_Counter_vhdl/08bits`). Written under `param_domains`, it
moves that replacement, or adds a second one: by default, the configuration is
written into `param_target_file` instead of the design, with the delimiters of
the architecture unless they are given here.

{{< code lang=yaml filename="_settings.yml" >}}
architectures:
  - Example_Counter_vhdl:
      param_domains:
        __main__:
          param_target_file: "tb/tb_counter.vhdl"   # the testbench gets the width
{{< /code >}}

> [!WARNING]
> The top-level `use_parameters` / `param_target_file` / `start_delimiter` /
> `stop_delimiter` keys, and the `override_parameters` / `override_param_file` /
> `override_param_target_file` / `override_start_delimiter` /
> `override_stop_delimiter` keys, are **deprecated**. They still work and still
> run, but they only ever covered a single replacement each. Express both with
> the syntax above instead: the first ones are a `__main__` replacement, the
> `override_*` ones a [simulation-only domain](#simulation-only-domains).
> `odatix migrate` lists the simulations still using them.

## Invariant domains

| Key | Type | Description |
|-----|------|-------------|
| `invariant_domains` | list or mapping | Parameter domains this simulation's result does not depend on. |

Declaring one has two effects: only **one** value of that domain is simulated
instead of all of them, and the result carries no such dimension — so a
synthesis result borrowing a metric from this simulation gets it whatever the
value of that domain.

{{< code lang=yaml filename="_settings.yml" >}}
invariant_domains: [MEM]          # let Odatix pick which value runs
{{< /code >}}

{{< code lang=yaml filename="_settings.yml" >}}
invariant_domains:
  MEM: 1024I_1024D                # run this one
{{< /code >}}

See [Derived metrics](/docs/results/derived_metrics/) for why this matters when
simulation and synthesis figures are combined.

## Templates

Odatix provides a simulation for each of these simulators. Each one compiles,
elaborates and runs the design under test and its testbench, as
[`odatix_sim.yml`](#what-odatix-tells-the-simulation) describes them: nothing
in it is specific to a design.

| Template | Simulator | Languages | Commands |
|----------|-----------|-----------|----------|
| `ghdl` | GHDL | VHDL | `ghdl -i`, `ghdl -m`, `ghdl -r` |
| `verilator` | Verilator 5 | Verilog, SystemVerilog | `verilator --binary`, no C++ to write |
| `questa` | Questa, ModelSim | VHDL, Verilog, SystemVerilog, mixed | `vlib`, `vcom`, `vlog`, `vsim -c` |
| `xsim` | Vivado simulator | VHDL, Verilog, SystemVerilog, mixed | `xvhdl`, `xvlog`, `xelab`, `xsim` |
| `icarus` | Icarus Verilog | Verilog, part of SystemVerilog | `iverilog`, `vvp` |

There are two ways to use one.

**Name it in a run**, with no simulation directory at all:

{{< code lang=yaml filename="sim_settings.yml" >}}
simulations:
  - questa: [Example_Cordic_sv/*, Example_Cordic_vhdl/*]
{{< /code >}}

The testbench then comes from the architecture (see [`testbench` in the
architecture settings](/docs/reference/architecture/#testbench)).

**Start a simulation from it**, with the `template` key, and say only what
changes, usually the testbench:

{{< code lang=yaml filename="simulations/TB_Cordic/_settings.yml" >}}
template: xsim
testbench:
  top: tb_cordic
  files: [tb/tb_cordic.sv]
{{< /code >}}

| Key | Type | Description |
|-----|------|-------------|
| `template` | string | Template the simulation starts from. |

The simulation's settings are the template's, merged with its own: a mapping
key by key, anything else (a list of tasks, for instance) replaced. Its work
directory gets the template's files first, then its own, which replace those of
the same name: a simulation holding a `run.py` runs its own. A template can
itself start from another one.

A simulation is looked up by name in the workspace first, then among the
templates: a simulation called `questa` replaces the template for the whole
workspace. If it says `template: questa`, it starts from the one Odatix
provides.

### Languages

A template declares the languages its simulator compiles:

| Key | Type | Description |
|-----|------|-------------|
| `languages` | list | `vhdl`, `verilog`, `sv`. A design written in another one is refused when the run is checked. |
| `test_command` | list | Command telling whether the simulator is installed. |

Running `verilator` on a VHDL design is reported before anything starts, with
the design in the list of invalid jobs. So is a simulator whose `test_command`
is not in the `PATH`: every job of the run would fail otherwise.

### What a template reports

Every template writes `sim_report.yml` in the job's work directory, which its
`_metrics.yml` exports:

| Metric | Value |
|--------|-------|
| `sim_status` | `passed`, or `failed` when a command failed or printed an error. A failed simulation is exported too. |
| `sim_errors`, `sim_warnings` | Errors and warnings the simulator printed. |
| `compile_time`, `elaboration_time`, `simulation_time` | Time spent in each stage, in seconds. |
| `simulated_cycles` | Cycles the testbench simulated, when it prints `odatix_cycles: <n>`. |
| `cycles_per_second` | Simulated cycles per second of simulation time. |

A simulation starting from a template adds its own metrics in its
`_metrics.yml`: both files are read, and a metric of the same name replaces the
template's.

Each command's output is kept in the job's `log/` directory, and the progress
is written to `log/progress.log`.

### Writing a template

A template's script is `run.py`, a short Python script built on
`odatix.sim.runner`. Copy one of Odatix's into a workspace simulation of the
same name to change it:

{{< code lang=python filename="run.py" >}}
from odatix.sim.runner import SimRunner, parameter_args

sim = SimRunner("ghdl", languages=["vhdl"])
options = ["--std=08", "--workdir=ghdl_work"]
sim.run("compile", ["ghdl", "-i"] + options + sim.files("vhdl"))
sim.run("elaborate", ["ghdl", "-m"] + options + [sim.tb_top])
sim.run("simulate", ["ghdl", "-r"] + options + [sim.tb_top]
        + parameter_args(sim.tb_parameters, "-g{name}={value}"))
sim.finish()
{{< /code >}}

`sim.compile(files, command)` compiles the files all at once and, should the
order be wrong, one by one until they all compile: the last resort when the
[compilation order](#compilation-order) Odatix computed is not the right one.

## `_metrics.yml`

Optional, and identical in format to a workflow's — see
[Metrics files](/docs/reference/metrics/). It declares what to extract from each
run; results land in `results/results_simulation.yml`, whether the simulation
passed or failed. A simulation with no `_metrics.yml` exports nothing, which is
fine for a testbench that only has to pass.

Every record also says how its run ended, as `sim_status`: `passed` when every
task succeeded, `failed` otherwise, unless the metrics define `sim_status`
themselves, as those of the [templates](#what-a-template-reports) do.

A metric holding text, such as `sim_status`, is not plotted by
[Odatix Explorer](/docs/features/explorer/), but it can be shown in a table,
filtered on and colored by, like a dimension.

An architecture whose runs report something else names its own file with
[`metrics_file`](#architectures), which then replaces `_metrics.yml` for that
architecture alone.

{{< code lang=yaml filename="simulations/<sim>/_metrics.yml" >}}
metrics:
  Cycles:
    type: regex
    settings:
      file: log/sim.log
      pattern: "Total cycles: ([0-9]+)"
      group_id: 1
    format: "%.0f"
    unit: cycles
{{< /code >}}

## In the GUI

**RTL Architectures** → **Simulations** edits this file, with the same task
editor as workflows, and the metrics editor for `_metrics.yml`. See
[The Odatix GUI](/docs/gui/app/).

The **Template** card of the Simulation Editor chooses the template the
simulation starts from, and says what it brings: the languages it compiles,
its tasks, its progress tracking and its metrics. The **Testbench** card sets
`testbench`; an empty field shows, greyed, what the simulation inherits, or
what happens without it.

**Run jobs** → *Simulations* lists the templates after the simulations of the
workspace. Their dropdown only offers the architectures written in a language
the simulator compiles (and those whose RTL is generated, which is only known
once generated). **New simulation from it** opens the Simulation Editor on a
new simulation starting from that template.

The **Simulators** section of the **Tools** page lists the templates, the
languages each one compiles, and whether its simulator is installed: its
`test_command` is run when the page opens.

**Run jobs** → *Simulations* shows only the architectures a simulation lists.
The cross next to an architecture takes it out of the list, and the dropdown at
the bottom of the simulation card puts one back. Both are edits like any other:
the **Save** button turns orange, and `architectures` is written to this file
when you press it.

Each card of the **Parameter Domains** section of the [Simulation
Editor](/docs/gui/app/) carries an **Architecture** field holding the
architecture the override applies to — wildcards included, and `*` for every
architecture. Two cards with the same domain name but a different architecture
are two independent overrides. Editing them never touches what else an
architecture entry holds, so a `metrics_file` set by hand survives.
